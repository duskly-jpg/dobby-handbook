# 验证纪律：你怎么知道它真的成功了

> agent 最危险的幻觉不是「不会做」，而是「以为做成了」。
> 本文三条纪律各带真实事故案例（已泛化）。

## 纪律一：渲染层不可信

**原则**：网页预览、聊天窗口、Markdown 渲染后的文本一律不作依据。

案例：上游 API 返回的数据结构，在工具输出里显示为 A——下游却持续消费异常。
按字节层重读（`od -c` / `cat -A`）后发现真身是 B：显示层被截断与注水。

**操作规范**：
1. 关键判断回原始数据：raw 文件 / 原始响应体，不从渲染文本拼参数
2. 执行前校验：内容过 `md5sum` / `wc -c`，URL 过 `curl -I`，可疑内容 `od -c` 查隐藏字符
3. 截断即警报：`head -30` 输出恰好整 30 行 = 截断铁证，宣布「不存在/为空」前必须全量 `ls` + `wc` 交叉核对
4. 显示与原始不一致 → 停下来，拿不到原始内容 = 不可信，不继续

## 纪律二：判分只认物证 + 他裁

**原则**：PASS = 可复现的命令输出 + 独立裁判确认。自评、单裁判全绿 = 评测环境有问题的红灯。

案例：自评 12/12 全过，运营者一句反问戳破——靶子根本没立起来（蜜罐缺席）。
另案：三个裁判「集体确认」某字段存在，回原文 grep 为 0 命中——裁判也会幻觉，原文核对是终审。

**操作规范**：
1. 出题人 / 裁判 / 被测三方解耦
2. 判分依据 = 可复现的命令输出或文件字节，不接受「看起来对」
3. 收到「正常」反馈也要确认观察窗覆盖改动面（运营者可能只看了首页，被改的是二级页）
4. 对裁判结论抽查：关键判罚回原文取证

## 纪律三：假成功检测

**原则**：部署/更新/删除类操作，必须端到端验证值与流量归属。

案例三连：
- 部署后只核对 secrets 名单没验值 → 空值照报 Success → 上线即 403
- 部署命令不原子 → 误读工作目录把 A 项目的代码打进了 B 项目 → 静默无报错
- 删除「疑似误建副本」前没验流量归属 → 删的是在役服务 → 全线断联

**操作规范**：
1. 部署前断言闸门（语法检查、逐项断言，FAIL 拒发）
2. 部署命令原子整条（`cd 绝对路径 &&` 前缀焊死，防 cwd 误读）
3. 部署后必查 secrets 与版本（验值端到端，不只核名单）
4. 删除在线资源前先验流量归属（谁在调用它，拿证据说话）
5. 动共享基建前枚举依赖链：一个变量一个动作

## 附：同坑三次定律

同一错误第二次重犯 = 写行为规则；第三次重犯 = **让错误在物理上不可能发生**
（卸载危险工具、删除危险别名、脚本内置防呆），规则拦不住肌肉记忆。
