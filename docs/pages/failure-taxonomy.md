# 失败分类学：agent 到底会怎么死

> 语料：某长周期生产 agent 的 30 起真实事故，逐案取首犯归因编码。
> 分类框架：规划 / 工具 / 验证 / 成本（可迁移到任何 agent 的失败复盘）。

## 统计

| 类别 | 占比 | 定义 | 典型形态 |
|---|---|---|---|
| **验证** | 33% | 判断「成功/正确」的环节失守 | 自评造假、假成功输出、基线误读、缓存假象、审查面没覆盖改动面 |
| **工具** | 30% | 对工具/环境的认知或使用出错 | 库里有现成刀没找到、部署命令静默顶替、截断输出当全貌 |
| **规划** | 30% | 动手前的侦查与实验设计不足 | 没做零改动对照、多变量齐发无法归因、撞车已有方案 |
| **成本** | 7% | 收益未证实就投入 | 无实测数据就上优化、冒烟通过还擅自加码放量 |

## 关键发现

1. **验证是系统性短板**：除 10 起首犯案外，还有 12 起案件把验证列为共犯——
   部署类、改包类、评测类大案几乎都缺一道「独立的成功判定」。
2. **工具类有根治解**：进程误杀类教训演进三次后，最终解是「物理上让错误不可能发生」
   （卸载危险二进制），而不是继续写行为规则。
3. **规划类靠 preflight 压制**：动手前强制检索既有知识（知识库/记忆/当日任务状态）
   能拦下一半撞车与重复造轮。
4. **成本类样本少≠风险低**：多数是运营者主动管控（叫停、限预算）前置拦截的结果。

## 复盘编码方法

- 每案只取**一个**主类（首犯归因），避免分类漂移
- 副类单独记（验证常是共犯），统计时区分「首犯占比」与「涉及占比」
- 主类占比随时间的变化本身就是 agent 健康度指标：验证类占比下降 = 纪律生效
